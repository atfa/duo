为什么是两个 Agent

一个 Agent 检查自己，仍然只有一种视角。

单 Agent 可以在同一个上下文里写完代码又批准代码。Duo 让审查在结构上独立：两个会话、两个工作树、一个双方都能检查的 commit。

Austin · 实现者

在自己的工作树里实现。

在自己的分支与检出中工作。完成约定的任务，以可审查的粒度提交，并给出 Duo 验证所需的证据。

  • 自己的分支与工作树
  • 提交带有确切 SHA
  • 附上测试与构建结果
Tony · 独立验证者

验证确切的 commit。

在另一份检出中阅读真实的 diff。在 Goal 与 Step 中，Tony 还会共同设计计划，并在签字前交叉审查实现。

  • 独立的检出
  • 阅读真实 diff
  • 签名绑定 SHA

平级，而非 subagent。Tony 拥有自己的上下文和工作树。Tony 不会对一份摘要盖章，Austin 也不会编辑 Tony 的检出。

因为重要的事，值得多一份认真。

Think Twice. Build Better.

工作流

选择适合任务的严谨程度。

同样的两个 Agent，三种协作策略。可以在运行中切换模式；协议名称在任何语言中保持原样。

Fast duo

多一双眼睛，再交付。

Austin 实现，Tony 独立验证确切的 commit，Duo 交付经过验证的结果。

TASK 你描述任务01
AUSTIN 实现并提交02
TONY 验证该 commit03
DELIVER 交付到你的分支04
适合 边界清晰的修复与小功能
Goal duo --mode goal

先谈好计划，再交叉审查。

两个 Agent 先就共享计划达成一致，各自独立工作，并审查对方确切的 commit。双方必须为同一个干净的集成 HEAD 签字。

PLAN 双方同意并签字01
EXECUTE 并行工作02
REVIEW 交叉审查03
INTEGRATE 双方为 HEAD 签字04
适合 架构调整与高风险重构
Step duo --mode step

一次只落地一个经过验证的增量。

双方先商定有序队列。每一步在下一步开始前落地，按 Fast 或 Goal 策略执行；队列可以跨重启保留。

PLAN 有序队列01
STEP 1 落地并验证02
STEP 2 落地并验证03
DONE 已交付04
适合 迁移与长周期任务

如何落地

从想法到你的分支，有四道检查点。

每个检查点都由 Git 背书，而不是一句聊天消息。证据一旦对不上，关卡就会关闭。

01 / ISOLATE

两个工作树，两个分支。

每个 Agent 在会话目录下拥有自己的检出。并行修改会变成一次显式的合并，而不是静默覆盖。

worktrees/20261022-211328/austin · worktrees/20261022-211328/tony
02 / COORDINATE

一份双方签过字的计划。

在 Goal 与 Step 中，只有双方批准同一份计划或步骤队列版本后，工作才开始。任何修改都会创建新版本并重置双方签字。

plan v4 austin ✓ tony ✓ · 任何修改重置双方
03 / VERIFY + SIGN

批准针对一个 commit，而不是一种感觉。

验证会阅读真实 diff 并运行检查。签名绑定被审查的 SHA；分支一旦移动，旧批准立即失效。

austin 6f2a1c9 · tony signed 6f2a1c9 ✓
分支移动 → 签名撤销
04 / DELIVER

只在可证明安全时移动。

在最后的 fast-forward 之前，交付全程只读。如果你的仓库有未提交改动，或分支无法 fast-forward，Duo 会拒绝并且不做任何修改。

deliver main ← verified HEAD (fast-forward only)
有未提交改动 → 拒绝，检出保持不变

为真实工作而建

表面很小，机制很重。

一个 Go 二进制协调会话、Git 状态与关卡。Agent、模型与仓库仍然属于你。

确定性的核心

阶段、关卡、路由与交付由 Go 强制执行，而不是在提示词里即兴发挥。Agent 只能通过核心授权的工具行动。

internal/project · internal/coordinator

绑定 commit 的证据

签名、验证与交付都引用确切的 SHA。恢复时，Git 已无法证明的批准会被撤销。

duo_status · session snapshots

冲突，而不是丢失工作

独立工作树把竞争变成可见的合并冲突。没有静默覆盖，未提交的工作会留在原处。

无文件锁 · Git 即边界

会拒绝的交付

在触碰你的检出之前，Duo 会证明这次移动是 fast-forward 且工作树干净。否则它会停下，不做猜测。

只读检查 · 仅 fast-forward

恢复与继续

计划、队列与对话记录都会持久化。崩溃后，恢复会用 Git 证据核对批准，并保留队列位置。

duo resume · 日志重放

快速开始

两条命令，得到第二个意见。

安装二进制，在任意 Git 仓库中运行，然后描述任务。Duo 负责工作树、关卡与交付。

01

安装

macOS 或 Linux，amd64 或 arm64。也可以使用 Go 1.24+ 从源码构建。

curl -fsSL …/install-release.sh | bash ./scripts/install.sh
02

在仓库中运行

Fast 是默认模式。需要协商计划或有序队列时再切换。

duo duo --mode goal duo --mode step
03

审查并推送

Duo 会把验证过的结果交付到你启动时所在的分支。检查 commit、运行你自己的测试，满意后再推送。

your-repo — duo 
$ cd ~/projects/your-repo
$ duo --mode goal

duo v0.13.1  ·  goal  ·  pi
──────────────────────────────────────
  austin  plan      计划已共同确认
  tony    plan      计划已共同确认
  phase   execute

  austin  working   src/auth/session.go
  tony    waiting   等待确切 commit

  gate    verify → sign → deliver

需要 Git 与至少一种受支持的 Agent CLI。Agent 以你的权限运行——工作树隔离修改，但不是安全沙箱。

常见问题

工程师最先会问的问题。

这和 subagent 有什么不同？

不同。Subagent 与父会话共享同一工作树；Duo 运行两个独立的 Agent 会话，拥有各自的工作树与分支，它们的批准绑定到真正审查过的 commit。

需要两个模型或两个 API key 吗？

不需要。可以让两个 Agent 使用同一个 driver，也可以用 --austin-driver 与 --tony-driver 分别指定。内置 driver 为 pi、agy、opencode 与 codex。

两个 Agent 修改同一个文件会怎样？

每次修改都落在各自的分支，所以结果是在集成阶段出现一次普通的 Git 冲突——可见、可解决。Duo 不会为了强行合并而丢弃未提交的工作。

验证失败会怎样？

关卡保持关闭。Tony 针对该 commit 报告问题，Austin 在自己的工作树中修复；新的 commit 需要新的验证，旧签名不会延续。

Duo 会改写我的历史吗？

不会。交付只会 fast-forward 你启动时所在的分支。如果无法做到，或工作树有未提交改动，Duo 会拒绝并保持检出不变。

我的代码会离开本机吗？

Duo 是本地 Go 二进制，没有托管后端。提示词会像没有 Duo 时一样发送给你的 Agent 提供商；协调、工作树与证据都留在本地。

开源吗？

是，MIT 许可。源码、issue 与发布都在 github.com/atfa/duo。
